# 当前 DCVLM 预处理时间预算

日期：2026-10-23。这是基于已核对规模和既有实测的条件预算，不是全库实测工期。

**若目标是近一亿张图完成 AI 筛选、SSCD 与索引发布，可暂按 2–4 周安排机器处理窗口，前提是集群达到持续 100–200 图／秒的有效流水线吞吐，并完成模型常驻与索引扩容。当前单机 CPU 执行方式不能直接承诺这一工期。** production 图像筛选 v3 已将 DataComp、ReLAION 等 mixed／unknown 来源路由到检测，因此预算必须覆盖主体网页数据的实际检测工作量，不能按旧前置门跳过的数据量计算。该窗口不包括来源证据整理、代码扩容开发和人工未决队列清零的时间。

## 已核对的规模

直接读取当前原始父版 `dcvlm_pretrain_v1_20261016T062238Z/manifest.json`，没有引用已退休的 T2I50 方向统计：

- 119,010,208 条记录。
- 108,026,384 次图像引用。
- 发布构建统计中的独立已解码图像为 99,856,885 张；这不是本轮重新全库去重的结果。
- 88,908,841 条原生 caption；22,096,237 条纯文本对话不需要图像模型。

默认不全量 recaption、不逐图判断 layout，因此此前“全量 caption API 约 200 天”的算例不适用于当前方案。

## 计算量与吞吐情景

| 集群实际有效吞吐（假设，未实测） | 约 9,986 万独立图像所需时间 | 未复用重复引用、按 1.08 亿图槽计算 |
|---|---:|---:|
| 100 图／秒 | 11.56 天 | 12.50 天 |
| 200 图／秒 | 5.78 天 | 6.25 天 |
| 500 图／秒 | 2.31 天 | 2.50 天 |

这些速率指实际受读图、检测、SSCD 和索引限制后的有效处理率，不是单个模型的瞬时峰值，也没有假设某个数量的昇腾卡必然达到该速率。读图、索引、重试、API 和尾部积压需另外预算或与主流水线重叠执行；以 100–200 图／秒为目标并留出这些余量，得到上述 2–4 周机器处理预算。

现有 CPU 实测为 2,396 张图：CF384 164.6 秒、UniFD 580.7 秒，两者串行合计约 **3.21 图／秒**。若每张独立图都需要两者，仅这一步约 **359.5 天**，尚未计模型加载、SSCD、完整索引或 API。这是全图检测的负载情景；实际可扣除已验证保护来源与有效缓存，但 mixed／unknown 标签本身不能扣除检测工作量。[检测器实测](detector_calibration/REPORT.md)

当前实现还存在明确的规模边界：检测器缺失分数使用 CPU 子进程；SSCD 历史 HNSW 在批次路径中重建。它们适合当前有界验证，但不能通过仅提高 `--model-concurrency` 就变成亿级执行方案。正式运行需模型常驻、批推理、按分片调度和复用／持久化 ANN；现有按 SHA 的裁决与缓存复用也需要在全库负载下测量。分阶段功能验证与这些全库性能工作分别记账。

## API 是否拖慢整个任务

Qwen 的既有 caption 任务测试约为 5 条有效响应／秒；AI 警报复核、近重双图复核与缺失 caption 的耗时不同，下面仅借这个速率作容量情景，**不是已测得的复核吞吐或实际触发比例**：

| 假设需要一次 API 的独立图像比例 | 请求量约 | 以 5 次／秒计算 |
|---|---:|---:|
| 0.1% | 10 万 | 5.55 小时 |
| 1% | 100 万 | 2.31 天 |
| 5% | 500 万 | 11.56 天 |

需要两次调用的样本相应增加请求工作量；不同 API 分支应合计。API 可与读图／模型推理重叠排队，不能机械把所有表格时间相加。人工不确定项另外发布待办，不应让少量人工队列阻塞整批已完成索引。[Qwen 实测范围](API_QWEN_THROUGHPUT_REPORT.md)

## 来源标签决定检测负载，不代表淘汰比例

按精确父来源合同与发布图槽统计关联，mixed 为 102,949,224 次、unknown 为 3,304,515 次，合计约占 **98.36% 图像引用**；natural 为 570,480 次、programmatic 为 1,202,165 次。这是来源级工作量清点，尚未做本轮全量逐记录最终判定。图像引用也不等于唯一图片，不能直接把该比例乘到独立图像数上当作精确检测量。

旧 production 前置门曾把这些标签直接转成 pending，导致主体网页数据无法进入检测；此前“约 98.36% 被来源门卡住”的说明记录的是这个已纠正的问题。当前 v3 对 mixed／unknown 图片执行 Community Forensics＋UniFD：无警报按筛选策略准入，有警报交给 Qwen，仍无法判断的才进入待处理队列。来源标签保持不变，不将通过筛选改写为已证明自然图。明确 AI、图像关联／结构错误和原始短边小于 128 的规则继续执行。

因此 **98.36% 既不是当前 pending 比例，也不是 AI 图片比例**；它提示主体图像引用需要纳入检测负载。v3 全库警报率、API 调用比例、最终准入率与持续吞吐尚未测得，上面的 2–4 周仍是未验证的条件预算。基础 stage1 `run/export` 不运行检测，其 `quarantine` 不应作为完成筛选的结果或时间依据。

可复算规模数值及清单指纹见 [capacity_estimate.json](validation/staged_refactor_20261023/capacity_estimate.json)。旧前置门下的 33 条真实 DCVLM 验证和 264 项回归测试是历史证据，不代表 v3 检测后的放行率或性能；各次实际结果及最新验证范围见 [重构报告](REFACTOR_REPORT_20261023.md)。
