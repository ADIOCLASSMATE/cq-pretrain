# 当前 DCVLM 的处理时间与容量估算

本次只读核对已有元数据、模型回执和引擎日志，没有新模型请求，也没有改变部署或启动全量处理。

**如果约 8,891 万条 caption 都重新生成长、中、短描述，当前已测吞吐对应十几年至几十年的计算量。** 这是指定工作量下的容量算例，不是可靠的全库 ETA，也不是 32 张 910B 的性能上限。当前执行器仍是先导配置，存在明显的供给不足；正式生产必须先调整调度并测长输出稳态吞吐。

## 分母：已核实原始父版

数据根目录：`/inspire/sj-ssd3/project/high-dimensionaldata/public/datasets/dcvlm_pretrain_v1_20261016T062238Z`。

直接核对该目录的 `catalog.json`、`manifest.json`、`COMPLETE.json` 与 `reports/statistics.json`。12,205 个分片的元数据 rows 求和与发布统计一致；不是沿用 T2I50 的方向分布。

| 原生格式 | 记录数 |
|---|---:|
| caption | 88,908,841 |
| 含图 conversation | 3,507,428 |
| interleaved | 4,497,702 |
| 无图 text_conversation | 22,096,237 |
| 合计 | 119,010,208 |

含图记录合计 96,913,971；图像出现 108,026,384 次，构建统计的 `unique_decoded_images` 为 99,856,885。图像资产、图片出现次数和完整记录不能混作同一分母。caption 占含图记录的 91.74%；DataComp 与 ReLAION 合计占 caption 的 98.58%，因此领域均衡的 19 条 canary 不代表全库工作量分布。

当前代码对纯文本同样调用 Qwen 生成和 Gemma 复核，只是不进入图像分支。下文仅计 caption，不是假定现有代码已自动跳过 2,210 万条纯文本。初筛保留率、精确重复复用率、重生成率和人工处理比例没有全库代表性估计。

## 已测吞吐与不足

配置为 Qwen3.5-397B-A17B BF16 32 卡，加 Gemma4-31B-IT BF16 4 卡。HIGH/LOW 是调度优先级；以下首先假设服务已经可用且全天运行，未计排队和抢占等待。

首轮真实生产的 Qwen 引擎日志：UTC 17:50:01–17:53:51，共 24 个约 10 秒桶，4 个 DP 合计平均约 **39.23 输出 token/s**，中位数 42.2，峰值 79.2。该数已经是整 32 卡合计，不能再乘 4。Gemma 对应活跃日志窗口平均约 13.49 输出 token/s。两者窗口不完全相同，且含空闲，不能直接相除判断硬件效率。

当前生产默认 record 并发 4、共享 model 并发 6；首轮 Qwen 最多 4 个 running 请求，Gemma 最多 3 个，没有引擎等待队列。四个 Qwen DP 的输出份额约 29.5%／38.7%／22.5%／9.3%。生成后才进入复核，任务长短差异会造成空闲；当前测到的不是长输出满载上限。

16／32 并发的短 OCR 测试中 Qwen 最高约 89 输出 token/s；Gemma 约 40.6。每请求仅约 69 输出 token，不能直接替代长描述、长上下文、多图任务。Gemma 并发 16→32 几乎没有吞吐增长，实际出现 8 Running／24 Waiting；增加请求数量不等于等比例增加算力。

首轮 19 条流程用时 234.61 秒，包含 layout、两条多轮的协议失败重试和不均匀供给；第二轮 96.17 秒复用了 14/18 个最终生成结果。两者均不能直接用记录数除耗时，得到可承诺的全库速度。缓存没有每请求 start/end/TTFT，当前无法精确拆分排队、图像编码、prefill 与 decode。

## 可复算的 caption 工作量情景

两条 COCO caption 首次生成分别输出 498／367 token，均值 **432.5 token/记录**，已包含短中长及协议字段；Gemma 对应 92／77 token。只有两条，不是网页 caption 全库平均值，也不是统计置信区间。

以 88,908,841 条 caption 全部保留并逐条重生成、平均 432.5 输出 token 为明确假设：

`Qwen 计算天数 = caption 数 × 每条输出 token ÷ 整服务输出 token/s ÷ 86400`

| Qwen 持续输出能力 | 每 100 万条 caption | 全部 8,891 万条 caption |
|---|---:|---:|
| 39.23 token/s，当前小样本生产窗口 | 约 128 天 | 约 31.1 年 |
| 50 token/s，假设持续能力 | 约 100 天 | 约 24.4 年 |
| 90 token/s，假设长输出也能维持；尚未验证 | 约 56 天 | 约 13.5 年 |

这只算 caption 生成工作量，尚未包含其他记录、额外 layout／重试／复核导致的瓶颈、人工队列和低优中断。各阶段独立并行时，理想流水线看最慢阶段，不能简单把所有模型时间相加；当前耦合调度还会产生额外空闲。

若最终仅有比例 f 的 caption 需要重生成，生成工作量近似乘 f；其他过滤扫描仍需执行，不能一并按 f 消失。假设低优有效可用率 u，日历时间再除以 u，另加初始排队；例如 80% 可用率乘 1.25。目前没有实测 u，不伪造低优工期。

## 图像筛选也需要并行扩展

已有 CPU 试验：CF384 处理 2,396 图约 164.6 秒，UniFD 约 580.7 秒；两者串行约 3.21 图/s。SSCD 使用 8 CPU 线程，2,208 图约 172.95 秒，约 12.77 图/s。

若约 9,986 万个唯一图像全部走同一配置的两个检测器，机械外推约 360 CPU 工作日；SSCD 编码及该小索引试验机械外推约 91 天。这些不是全库实测，未覆盖大规模 ANN 成本、存储吞吐、来源保护分流和尺寸拒绝；不能直接作为正式筛选 ETA。现有每工作单元重建 ANN 的方式也须先改为分片常驻索引，否则亿级开销不同。

## 对生产排期的含义

若希望 90 天完成全部 9,691 万条含图记录，需要平均约 **12.46 条完整记录/s**。仅 caption 生成、沿用上述 432.5 token 假设，就需要约 **4,945 输出 token/s**，另配足够的复核、图像筛选和存储能力。相较当前生产窗口差约 126 倍，相较短 OCR 89 token/s 约 56 倍；这只是容量差，不是可承诺的线性扩容倍率。

优先改进顺序：

1. 来源与 schema 预判、尺寸检查和精确资产去重前置；未知来源隔离后不为正式生产无差别生成 audit-only 标注。保留必要的独立审计样本。
2. 图像资产只算一次检测、特征与图像级 caption；保留不同任务／问题／上下文的监督，不把同图不同 QA 合并。可信原生 QA、OCR 与纯文本按各自任务路由，不默认全部重写。
3. 将生成、复核、layout 拆成独立有界队列，分别设置并发和背压；先验证长输出批处理是否能持续供满 Qwen 的四个 DP，再判断需要多少副本。仅增加前端并发不是最终方案。
4. 以占主体的 DataComp／ReLAION caption 为主要权重，补充文档／多轮／交错等分层冷缓存基准；按原图尺寸、上下文和生成长度记录端到端吞吐、质量、重试率与缓存收益。不能仅把两条 COCO 的均值当正式预算。

现有代码还不是可直接运行 1.19 亿条的分布式调度器；正式 ETA 需在来源准入工作量和长输出稳态吞吐得到测量后给出。本次结论是：**当前功能验收配置不适合原样启动全库重描述；应先优化生产调度和处理范围，再测扩容需求。**
