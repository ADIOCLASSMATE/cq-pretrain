# Qwen API 真实图像吞吐测试报告

汇总时间：2026-10-22T19:44:47.070893+00:00。运行目录沿用 `api_throughput_20261023`；请求的真实 UTC 时间以逐请求日志为准。

本轮后续调用已按要求限定为 Qwen。测试已结束，没有后台基准请求继续运行。结论来自当前付费 API 入口的实测，不是官方宣传速度，也不代表模型或服务的并发上限。

**128 并发、每批 512 次请求时，Qwen3.8-Max 原始格式有效吞吐为 2.67 条/s；仅作确定性字段规整后，可解析吞吐为 5.05 条/s。Qwen3.8-Flash 为 5.21 条/s。Max 的平均长描述约 170 个英文词，Flash 约 118 个词，因此二者输出工作量和质量不能视为相同。**

## 工作负载与计量方法

- 256 张不同 SHA 的真实 DCVLM 库内图片：192 张来自 caption 来源、24 张图表、24 张文档/OCR、16 张 CLEVR。它们用于速度与领域压力测试，未因此获得自然图像或训练准入资格。原图短边至少 128。
- 每次请求输入一张图，生成英文 short / medium / long 三条描述及不确定性数组。一次请求已经包含三种长度，不应再把请求数乘三。目标词数为 15–40 / 60–100 / 150–250，允许证据不足时缩短。
- 主表统一 v3 提示词、4096 输出 token 上限、显式关闭 thinking、60 秒整请求时限，SDK 与应用重试都为零。接口报告的 reasoning tokens 和 thinking blocks 为零。
- 32 并发使用前 128 张，64 并发使用全部 256 张；128 并发使用全部 256 张各两次，共 512 个独立请求 ID。512 次不是 512 张独立图片。各模型顺序测试，避免互相争用同一账户额度；时间窗口不同，仍受服务波动影响。
- 没有本地响应缓存；服务端报告的缓存读取 token 为零，但不能据此证明服务内部不存在其他缓存。保留原图身份和实际发送尺寸；图像在必要时整图缩小，不裁剪。
- 主吞吐分母是从开始发请求到最后一次尝试结束的整批时间，包含队列与超时长尾。图像预处理单独计时，不计入 API 吞吐。非流式 P95 是完整返回延迟，不是首 token 延迟。
- 所有“有效”“规整后”仅指 HTTP、返回模型标识、完整 JSON/schema 与请求 ID 检查通过，**不代表事实正确或可直接入训练库**。

词数用空白分词，统计规整后可解析的 Max 491 条、Flash 492 条，描述字符串不变。输出 token 采用接口 usage，不是本地重新分词，也不能据此保证模型之间 tokenizer 完全相同。Flash 的中、长描述平均低于提示词目标；没有把“非空字符串”冒充达到了长描述要求。

Max 的 232 条格式错误均为把顶层 `uncertainties` 放进 `captions` 内部。审计仅在字段集合完全匹配、顶层不存在冲突字段、类型正确时移动字段，再重做严格校验；描述字符串和请求 ID 不变。历史其他批次的字符串外尾逗号也单独分类，禁止补写缺失事实、覆盖冲突值或把截断答案当完整答案。**这是离线规整审计能力，尚未接入生产准入；原始成功率没有被改写。**

Max 的 HTTP 400 在 128 并发批次集中于 manifest 索引 78、204 两张图，各重复两次。较低并发也曾返回同样错误，不能直接归因于并发过高。当前只记录了安全的错误摘要，尚不能确定是图像限制、入口策略还是其他原因；这类错误应按错误类型处理，不能和超时一同无限重试。

## 对 DCVLM 的容量含义

已核实的原生 DCVLM 有 88,908,841 条 caption。下表是假设这些记录都逐条重描述、一天运行 24 小时且长期维持本次 API 输出率的容量算例。它估算相应数量的结构合格响应，不能保证每一条原始记录最终成功。

| 128 并发方案 | 每 100 万条 | 88,908,841 条 caption |
|---|---:|---:|
| Max：只接受原始格式 | 4.34 天 | 386.0 天 |
| Max：加入已验证的有限格式规整 | 2.29 天 | 203.6 天 |
| Flash：原始格式 | 2.22 天 | 197.7 天 |

`天数 = 记录数 ÷ 每秒结构合格响应数 ÷ 86400`。若只有比例 f 的 caption 需要重生成，这部分模型工作量近似乘 f；来源索引、尺寸扫描、去重等成本不会因此自动消失。

上述约 198–204 天不含独立事实质检、最终成功所需的重试/修订、AI 图像筛选、SSCD、存储扫描、人工队列、其他记录类型及 API 可用性波动。输入准备在最终两批各约 5.8 秒，也未计入 API 主吞吐。单轮三档 caption 不能代表多轮、交错多图或长文档任务。完整流程当前还不能给出可靠工期。

若希望仅 caption 生成在 90 天完成，需要约 11.43 条/s；本次 Max 规整后约 5.05 条/s，差约 2.26 倍。这个比例是工作量差，不是已经验证的线性扩容倍数。主表仍未触及已知服务上限，后续高并发与长稳测试应单独测量。

## 质量抽查与当前建议

基于同一 v3 提示词和 32 并发批次，重新查看首 8 张图的返回：每模型各有 7 条可审 caption，不能据此计算全库准确率。两模型的两张几何图总物体数 9 和 7 都正确，但仍有相对位置/排序问题。Flash 对低清首饰切工、人物手套与场景写得过度确定；一张泰文牌的转写及释义明显缺少像素支持，正确转写尚未独立核实。Max 对部分不明白色部件更保守，仍不等于整体正确。审阅来自本次图像检查，不是独立专家标注的真值。

在额外的双图随机数字/颜色控制中，Qwen3.8-Max 通过，Flash 读错部分数字；这只能证明该次控制表现，不能推广为整体 OCR 准确率。两模型都不能仅凭格式通过自动入库。

当前更适合把 **Qwen3.8-Max 作为高质量重描述的主候选**：本次规整后吞吐与 Flash 接近，输出更接近所需的中长描述长度。这个选择仍需代表性事实质检，不能凭 8 张图宣布质量胜出。Flash 可继续作为较短描述或轻量任务的候选，OCR 和复杂空间关系应单独验收。

生产接入应先落实：结构化输出契约或版本化有限规整；超时与 HTTP 400 分流；有上限的重试与隔离队列；来源/资产缓存；独立事实质检。保留已有高质量 QA/OCR/纯文本的原任务监督，不把本次单图 caption 压测扩大解释为所有数据都必须重写。API 也不会自动消除本地检测器、SSCD 和 Gemma 质检的吞吐瓶颈。
